Maximum Subarray: brute force vs single pass

By the end you will write two versions, one slow and obvious, one fast and clever, and show they always agree. About 25–30 minutes.

1. Understanding the problem

You get a list of whole numbers, some negative. Pick a contiguous slice (numbers sitting side by side, no gaps). Add them up. Find the slice with the biggest total, and report that total plus where the slice starts and ends.

Return (sum, start, end) as a tuple. Both indices are positions in the list, and end is included.

Rules: no max(), min(), sum(), slicing or imports. A list of only negatives returns its single largest element, never 0. They are banned so you practise the logic by hand.
Tie rule (my assumption, so both functions can agree): if several slices share the best sum, return the one that starts earliest; if that still ties, the one that ends earliest. Your examples have no ties, but a "must match on every test" rule needs one.

2. Prerequisite: slices, indices and running totals

A list is numbered from 0. In [4, -1, 2, 1], 4 is at index 0 and 1 is at index 3. A slice is described by its start index and end index. A running total is a number you keep adding to as you walk along, instead of re-adding everything each time.

3. How it works

Brute force: try every start and every end, add each slice up, remember the best. Simple, but slow: 9 numbers means 45 slices, 1000 numbers means about 500,000.

Single pass: walk left to right once and, at each number, keep one fact: the best total of a slice that ends right here. Click through the example. Yellow = the slice ending here, blue = the number we just reached, green = best slice seen so far.

Top row: the numbers. Bottom row: best total of a slice ending at that position.

Practice by hand

P1. [3, -1, 2]: best sum and indices?

Reveal4 at (0, 2). Dipping through the -1 is worth it because the 2 after it pays you back.

P2. [-4, -2, -7]: best sum and indices?

Reveal-2 at (1, 1). Every slice is negative, so the least bad single number wins.

P3. [2, -5, 3, -1, 2]: best sum and indices?

Reveal4 at (2, 4). The -5 is too costly to carry, so you start fresh at the 3.

P4 (tricky). [2, -2, 3]: two different slices give the best sum. Which does the tie rule choose?

RevealSum 3 at (0, 2), not (2, 2). Both total 3, and the earliest start wins.

4. Translating it into Python

Step 1: Empty list. Pick one convention (for example return None) and use it in both functions.

Why decide this before writing any loop?

RevealStarting values usually come from the first element, which does not exist for an empty list.

Step 2: Starting values for the best. Create the variables that remember the best sum and its two indices.

If best starts at 0, what goes wrong for [-3, -1, -2]?

RevealNothing beats 0, so the answer stays 0 and the indices never update. Start from a real element.
Stuck?
NudgeWhich value in the list is guaranteed to be a real slice?
Bigger hintA single number is a slice, so the first number is a valid starting best.
PseudocodeSet best sum to the first number, and both best indices to 0.

Step 3: Brute force loops. Choose each start, then each end at or after it, building the slice total without sum() or slicing.

When the end moves one step right, how can you get the new total cheaply?

RevealAdd just the new number to the total you already have. Reset the total when the start changes.
Stuck?
NudgeThe outer loop picks where a slice begins.
Bigger hintThe inner loop starts at the outer index, so a slice has at least one number.
PseudocodeFor each start: set total to 0. For each end from start to the last position: add that number to total; if total is strictly larger than the best, remember total, start, end.

Step 4: Single pass. One loop. Keep the running total of the slice ending here, and the index where that slice started.

Looking at the previous running total, when is extending worse than starting fresh?

RevealWhen the previous total is negative: it can only drag the new number down.
Stuck?
NudgeCompare "previous total + this number" with "this number alone".
Bigger hintStarting fresh also means the slice's start index becomes the current index.
PseudocodeIf the total before this number is below zero, begin a new slice here (total is this number, start is this index); otherwise add this number to the total. Then, if the total is strictly above the best, record it with the start and this index.
Tie warningTest [2, -2, 3]. If the previous total is exactly 0, extending keeps the earlier start, and the tie rule wants that.

Common beginner mistakes

  • All-negative list returns 0. Your best started at 0. Look at the setup lines.
  • Right sum, wrong end index. You moved the end without checking the sum improved, so trailing negatives crept in.
  • Right sum, wrong start (fast version). You started fresh but forgot to move the start index.
  • Versions disagree only on ties. Check > versus >=, and what happens when the running total is exactly 0.
  • Fast version is secretly slow. A loop inside the loop means it is not a single pass.

6. Reflection

Brute force checks every slice; the single pass keeps only the best slice ending at each position, because anything dragging the total below zero is better dropped. Writing both lets one check the other.

Q1. Why does a negative running total make "start fresh" the better choice?

RevealAdding a negative to the next number can only lower it, so the number alone is at least as good.

Q2. Roughly how many additions does each version do for 1000 numbers, and why does it matter?

RevealBrute force does about 500,000 (growing with the square of the length), the single pass about 1000. The gap grows fast with longer lists.

Q3. Why can matching on five lists never prove the versions agree, and what makes a test list worth adding?

RevealPassing tests only shows no failure so far. Good lists target places where a wrong idea would differ: all negatives, ties, trailing negatives, empty input.
